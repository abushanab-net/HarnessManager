Remote control for running sessions: what to take from T3 Code and Orca

Issue #1 chose to run each tool in its programmatic mode and build a chat view on top, the way T3 Code does. Since it was written on 3 November, Claude Code and Codex have documented hooks that can answer a permission prompt from outside the terminal. That makes a cheaper design possible: leave the session in the tool's own terminal, as Orca does, and add a side channel for "needs you", approve, deny and reply. This plan takes the session model from Orca, the access and state rules from T3 Code, and carries both over the links Harness Manager already has between computers.

The short answer

Can it be done?

Yes, for a narrow version

See what is waiting, approve or deny, reply and stop, from the app, another paired computer or a phone page. Harness Manager already has most of the transport: paired computers over mutual TLS, a hub that relays ciphertext, presence, and a transcript watcher.

Like T3 Code?

The remote, without the client

T3 Code replaces the agent's interface with its own threads. Matching that is a second product. The version that fits is a remote for the tools' own terminals: an inbox of requests and a reply box, with the full conversation staying where it is.

What makes it worth building?

One inbox for everything

Claude Code, Codex and OpenCode each have a first-party remote now, each for one vendor. Nothing shows every waiting agent across tools, accounts and computers in one list. Harness Manager already knows what runs where.

Where this sits against the positioning report. That report says to freeze issue #1, because Orca and T3 Code are far ahead on remote control and the project has no outside users yet. I still think the distribution fixes come first. This plan is how I would build the feature if you decide to, cut so that it extends the one thing the report says is hard to copy: knowing what happens on every computer you own.

How T3 Code and Orca do it

T3 Code: the server owns the agent

  • A server process "owns provider processes, terminals, Git, checkpoints, durable state". Desktop (Electron), web and phone are clients over "authenticated RPC" on HTTP and WebSocket.
  • It never runs the tool's own interface. Claude goes "through Anthropic's Agent SDK", Codex through the app server, everything else through ACP.
  • State is event-sourced into SQLite. "Unanswered questions survive reconnects."
  • Access is by one-time pairing link or QR, with scopes such as terminal:operate, tokens bound to a client key, and short-lived tickets for sockets.
  • Away from home: Tailscale, or T3 Connect, which allocates a Cloudflare tunnel after sign-in. Whether traffic is encrypted end to end is not stated.

Orca: the terminal stays, hooks report

  • Agents run in real terminals (xterm.js, a terminal daemon). A phone can type into one: "each typed character should go straight to the active terminal".
  • "Orca-managed hooks ... report working / waiting / done into the UI." The hook reads its endpoint from a file on every call, so a session that outlives the app still reaches it.
  • The phone has a "Needs you" list that "collects tool approvals and access requests", plus short replies such as continue.
  • It reads the tool's own transcript to confirm a sent message arrived, and will not send into a conversation another terminal may be writing to.
  • Pairing is a one-time code or QR; each client gets "a separate, revocable token". The phone is "a remote control for the desktop you already have running".

Both are MIT licensed, so borrowing is allowed. Both are TypeScript on Electron, and Harness Manager is Rust on Tauri, so what transfers is design, protocol shape and rules. Very little code can be copied.

The design

Two channels per session

  • Hooks, for structure. One small command, hrm hook, is registered for the events that matter: session start and end, permission request, notification, stop. It reads the event from standard input, forwards it to the session's hrm run using the address in its environment, and for a permission request waits for the answer. Claude Code and Codex use the same event shapes, so one command serves both.
  • The terminal, for input. hrm run starts the tool inside a pseudo-terminal it owns and connects the local window to it. A reply sent from elsewhere is written into that terminal as if typed; Stop sends the interrupt key. The tool cannot tell the difference, and the user at the desk sees it happen.

Why the phone goes through the hub or Tailscale

The issue plans a phone page served by the PC over home Wi-Fi first. That page would load, but a browser gives a plain http:// address on the local network no service worker, no notifications and no cryptography API. A phone remote without notifications misses its main use. Both need a real certificate, and Harness Manager already has two places with one: the hub behind Caddy, and a Tailscale name. So the phone page is served from the hub you host (or over Tailscale HTTPS), and requests are sealed with the ring key before they leave the PC, as journals are today. The hub relays them and still cannot read or forge one.

Notifications use the browser's standard Web Push. The message goes through Apple's or Google's push service with an encrypted payload, and no Harness Manager server is involved. On an iPhone the page has to be added to the home screen first.

Phases

Each phase ships on its own. Sizes are relative: S is a few focused changes in existing files, L is a new subsystem with its own tests.

Phase 0 · Four spikes S

Answer these before writing product code, and record the results in the issue.

  • Claude Code: in an interactive session, does the terminal prompt stay answerable while a PermissionRequest hook is waiting, and what happens when both answer?
  • Claude Code: does a PreToolUse hook answer AskUserQuestion in an interactive session, or only under -p?
  • Codex: the same permission round trip, and what the one-time "review and trust" step looks like for a hook Harness Manager wrote.
  • Windows: run Claude Code and Codex inside a ConPTY owned by hrm run. Check resize, paste, mouse and colours against a direct start, then type a line into it from a second process.

Done when each has a yes or no with a recording, and the plan below is adjusted to the answers.

Answered 23 Nov 2026 (spikes.md, Claude Code 2.1.330, Codex 0.171.0, installed tools against a local model fixture): 1. yes, both stay answerable and the first answer wins; 2. yes, also without -p; 3. partly, Codex hides its own prompt while the hook waits and shows it on the hook's timeout, and trust is per hook declaration, so a changed command or timeout asks for review again; 4. partly, typed input, resize, paste and interrupt from a second process work through direct ConPTY calls (portable-pty stalled), and mouse, colours and clipboard still need a side-by-side look in Windows Terminal.

Phase 1 · "Needs you" on this computer S

  • hrm hook, with the hook entries carried by each hrm run launch (claude --settings <file>), so no account file is written and a session started elsewhere is untouched. Codex follows once its one-time hook review is designed: the declaration must never change, and the per-session address travels in the environment.
  • Waiting, working and done per session in hm.db; shown on the session row, the Overview, the tray and a toast. A click brings the right terminal to the front.
  • The issue's Remote Control switch for Claude subscription accounts (--remote-control), as the stopgap it describes.

Done when a session started from the app that reaches a permission prompt shows as waiting within two seconds with no log polling, a session started outside the app is unaffected, and removing the account removes the hooks.

Phase 2 · Approve and deny from the app M

  • The permission hook holds the request; a card shows the tool, the command or file, and the tool's own options unchanged.
  • Open requests are stored with an id and an expiry. Past the expiry the hook steps aside and the terminal prompt stands.
  • Question cards for Claude Code (spike two said yes).
  • Codex hides its own prompt while the hook waits, so its cards get a short expiry, after which the hook releases without a decision and the terminal prompt appears. The hook command bounds its own wait as well, for both tools.
  • An answer that arrives after the terminal decided is dropped by request id.

Done when a command is approved and another denied from the app with the terminal untouched, answering in the terminal first closes the card, and closing the app mid-request leaves the terminal prompt working.

Phase 3 · From another paired computer M

  • Waiting state added to presence; requests and answers as new messages on the direct link, and as sealed blobs with an event on the hub.
  • The reading view follows a session that is still running on another computer: the growing end of the transcript travels over the same link.
  • A level per paired computer on the Computers page: see, decide, type. Existing pairs start at see.
  • Every remote answer is signed by the device that gave it and listed in a log on the computer that ran it.

Done when a request raised on one test computer is approved from the second over the direct link and again over the hub, a computer at "see" is refused, and the hub's stored blob does not open without the ring key. These fit the existing HRM_E2E_PEERS and HRM_E2E_HUB runs.

Phase 4 · Reply and stop L

  • hrm run owns the pseudo-terminal, behind a setting until it has proved itself, because it sits between the user and every session.
  • A reply box and Stop on the session, here and on a paired computer with the "type" level. The reply is confirmed when it appears in the transcript.
  • Refused while another driver holds the session.

Done when a follow-up typed on the second computer appears in the first computer's terminal and in the transcript, Stop interrupts a running turn, and with the setting off sessions start exactly as in 1.12.

Phase 5 · Phone page L

  • A static page served by the hub: the inbox, a session's reading view, Approve and Deny, the reply box.
  • Pairing by QR from a computer on the hub; the phone's key is listed and revocable like a computer.
  • Web Push for "needs you" and "finished".

Done when a paired phone on mobile data approves a request and sends a reply, a revoked phone gets nothing, and the notification arrives with the page closed.

Phase 6 · Tools without deciding hooks M each

OpenCode through its server (permission.asked events and a reply endpoint, with the tool's own interface attached to the same session), then others through ACP. Antigravity stays terminal-only, as the issue says. Build these when a user of that tool asks.

Security rules for this feature

Approving from another device runs code on the PC. These add to the rules in SECURITY.md.

  • Nothing new listens beyond this computer. The hook endpoint binds 127.0.0.1 with a token that exists only in the session's environment. Remote requests use the peer listener and the hub connection that exist today.
  • New devices can only look. Deciding and typing are granted per device, by hand, on the computer that runs the sessions.
  • Every remote action is signed and logged. A request carries an id and an expiry, an answer names the request and is signed by the device key, and a replayed or late answer is dropped.
  • The hub stays blind. Requests contain commands and file paths. They are sealed with the ring key like journals, so the hub sees who sent how much and when, and nothing else.
  • Logins are not involved. Only the unmodified tool runs, in its own terminal, under its own login. No token is read, stored or sent for this feature.
  • The app never widens a permission. It offers the options the tool offered. "Always allow" from a phone is off unless the user turns it on.

What is not known yet

  • Whether a waiting hook and the terminal prompt can both be live in Claude Code and Codex. The whole of Phase 2 rests on it. If the terminal blocks while the hook waits, the card needs a short expiry and Phase 4's typed answer becomes the main path.
  • Whether questions can be answered by hook in an interactive session.
  • How faithful a ConPTY wrapper is on Windows for these two interfaces. If it is poor, Phase 4 changes to "reply by resuming the session with a prompt after the turn ends", which is weaker.
  • I did not read Codex's pages on remote connections and mobile, Orca's Relay design, or how T3 Code delivers phone notifications. None of them changes the plan, but the first may show Codex already offers a first-party remote like Claude's.
  • Rust crates exist for the pieces (a pseudo-terminal, ACP, Web Push). Versions and Windows behaviour are to be checked in the spikes.
