Usage, sessions and backups across your computers

You work on the same repositories from several computers, and each Harness Manager only knows the logs on its own disk. This page analyses what it would take to see everything in one place, to pick a session up on another computer, and to keep the history through a reinstall. It sets out the options with their trade-offs, the diagrams of how each works, mockups of every screen that changes, and a feedback sheet at the end. Nothing is built yet.

Today: one computer, one picture

Each computer imports usage from the tools' own logs into its own SQLite database, indexes the session files it can see, and draws the Overview from that. Two things already cross computers, and both matter for the design: the account list (profiles.json) can live in a OneDrive folder, and a project's key is its git remote (github.com/owner/repo), which is the same on every computer that cloned it. Keys and logins never leave the computer, and that stays.

Each computer reads only its own logs. The account list is the one thing that can already be shared, through a synced folder.

The common core: a journal per computer

Whatever carries the data between computers, the data itself is the same, and most of the work is here rather than in the transport. Each computer gets a stable identity and writes an append-only journal of what it alone knows: usage rows (already keyed by a stable request_id, so merging is idempotent), its session index, its limit readings, and a small presence record, refreshed every minute, saying what is running. Every computer merges the others' journals into its own database. One writer per journal means no conflicts, ever. Each usage row carries its cost as valued when it was imported, with the price snapshot it used, so the history never moves when the price table does; a "at today's prices" view can be computed on top when wanted.

One journal per computer, merged everywhere. The transport in the middle is replaceable; the journal format is not.

How the journals travel: three transports

The transports differ in who holds the data, how fresh "live" can be, and what you have to run. You chose all three, in the order journal, presence, resume, backup; the hub and the peer designs each get their own section below.

A · Synced folder about 2 weeks

Point Harness Manager at a folder in OneDrive (or Dropbox, or an SMB share). Each computer writes <device>/journal-NNNN.jsonl and <device>/presence.json; every computer reads the others. No network code, no ports, no certificates, works over the internet because OneDrive does.

Gives R1, R3, R5 in full; R2 and R4 with a delay of OneDrive's sync (seconds on a LAN, up to minutes elsewhere).
Costs the "live" picture is a heartbeat, not a connection; a folder that stops syncing looks like a computer that went quiet; large transcripts go through the sync service.

B · LAN peers about 5 weeks

Each app announces itself on the local network, you pair two computers once with a six-digit code, and they talk over TLS. Presence is the open connection; journals are pulled with a cursor. Away from home, a VPN carries it.

Gives R2 as truly live, R3 as literally asked, R1 and R4 when both computers are on.
Costs the most code (discovery, pairing, certificates, firewall prompts on Windows); nothing arrives while the other computer is off, so R5 needs a backup anyway; does not cross networks by itself.

C · A hub about 4 weeks plus hosting

A small service you host (a VPS running Docker, or a Cloudflare Worker with D1 and R2) that every computer pushes its journal to and pulls the others' from. Journals are encrypted on the computer before they leave it.

Gives R1 to R5 from anywhere, and a natural off-site copy for R5.
Costs a service to run, patch and secure; an account and a token per computer; your usage data on a server, even encrypted; one more thing that can be down.
D · The hybrid is the same journal under a small transport interface. To you it is one choice in Settings: a shared folder (OneDrive, Google Drive, SMB, NAS) or a hub you host (the VPS, or a Worker), with the direct connection as an add-on on either for live routes within a second. The plan delivers both, the folder first and the hub after, and because the journal is the same, a computer can move from the folder to a hub later with every computer's history kept.

A session follows the project, not the path: the repository's remote maps to each computer's local folder, and the copy is a fork.

Rules that make it safe

  • Fork, never move. Resuming elsewhere makes a new session that starts from the old transcript. Both computers keep what they had; the Sessions list shows the fork as "continued from LAPTOP".
  • Sessions follow projects you have here. A session is offered only when this computer has the repository (the device record lists remote → local path). Otherwise the row says "LAPTOP · not cloned here".
  • Transcripts travel only if you say so. The default journals session metadata for everyone; carrying transcripts is a switch (per computer, with a size cap), because they can be large and contain your code.
  • Open sessions are not offered. A session the other computer is still running shows "running on LAPTOP"; resuming it here would fork mid-thought.

R5 · Backup, archive and a fresh computer

Today's backup is the account list, settings, the ledger and the managed skills. It does not hold usage, sessions or transcripts, so a reinstall starts the Activity grid from zero. Two additions close that:

  • The backup grows. The zip also holds an export of usage, limit history, the session index and tags, and (optionally) the archived transcripts. Restore merges it, so restoring twice or over a live database adds nothing twice.
  • Archive moves old transcripts out of the tools' homes into Harness Manager's archive (compressed, by project and month), after an age you choose. The session stays in the list with its numbers and a readable transcript; the tool's own folder gets lighter. Codex already does this itself with archived_sessions; Claude Code does not.

With the folder transport, the synced folder is the second copy: a fresh computer that joins it gets every other computer's journal and can rebuild the shared history on first launch. Its own old journal (the one the formatted computer wrote) is still there too, under the old device name, so nothing of that computer's past is lost.

Recovery is a merge: the folder carries the history of every computer, including the one being rebuilt.

The hub: three designs

A hub is the one transport that works when two computers are never on at the same time and when one of them cannot run a VPN. The three designs differ in how much runs on the hub: nothing, a small serverless function, or a service you operate. In all three the journals are encrypted before they leave the computer, so the hub stores sizes and times, never text.

A transcript is encrypted with the device key before it leaves; the recovery key, kept outside the computers, unwraps the device keys so a fresh install or another computer can read it.

H1A bucket only: nothing to run

Every computer puts immutable chunks and a signed manifest into a bucket; the others list and fetch. Presence is the manifest's age.

Any object store works: Cloudflare R2 or S3 with a scoped token per computer, or a share on the NAS (SMB, WebDAV). This is the folder transport with HTTP instead of a drive letter, which is why it costs about a week once the journal exists. What it cannot do is live presence or a rendezvous for peers: a computer learns of another by polling the manifests, every 30 to 60 seconds at best.

H2A Cloudflare Worker with D1, R2 and a Durable Object

A Worker fronts an index in D1 and blobs in R2; a Durable Object fans presence out over WebSocket and publishes each computer's reachable addresses for peers.

Serverless, nothing to patch, and the free tiers cover a journal that grows by kilobytes a minute. Each computer gets a bearer token at pairing; the Worker checks it, stores the chunk, updates the index, and tells the Durable Object, which pushes to every connected computer. The same Durable Object is the rendezvous for direct connections: a computer registers the addresses it can be reached at, and a peer anywhere looks them up. Presence over the WebSocket is live from anywhere, without a VPN, which matters for a work computer. Built and deployed with the cf CLI, per the house rule.

H3A self-hosted service on a VPS, in Docker

One container behind Caddy on a VPS, with Postgres and a volume copied nightly to a bucket; it also relays peer traffic when no direct path works.

A small VPS with docker compose: Caddy for TLS on port 443, one hm-hub container (the same Rust core as the app, so the journal code is shared), Postgres, and a volume for the encrypted chunks that is copied to a bucket every night. It is on the public internet, so every computer reaches it without a VPN, and it does what H2 does plus a relay with real bandwidth for peers whose hole punching fails. The price is operations: you patch the VPS and the images, watch the disk, rotate the nightly copy, and it is down when the VPS is. A one-line install (compose file plus an environment file) keeps that small.

Peers: how computers find each other, pair and sync

You asked for live routes within a second, which only a direct connection gives. Three things have to be designed: how a computer finds another, how two computers trust each other once, and what they say to each other afterwards.

Finding each other: three paths, one trust

The same pairing trust works over any path: multicast on the home network, stable names over a VPN, or addresses published through the hub with a relay as the last resort.

The app tries them in that order and shows which one it is using beside each computer on the Computers page. All three are behind one "Direct connection" switch; the folder and the hub keep working underneath, so a computer that cannot be reached directly is still merged, just not live.

Pairing once

A six-digit code and a password-authenticated key exchange: the code is never sent, a wrong code fails before anything is trusted, and each computer keeps the other's certificate.

Every computer makes itself a key pair and a self-signed certificate at install. Pairing shows a six-digit code on one computer, typed on the other; a PAKE (SPAKE2) turns it into a shared secret without sending it, and the two exchange certificates, names and device ids inside that secret. From then on every connection is mutual TLS with those certificates, over whichever path found the peer. Revoking a computer is deleting its certificate on the others, from the Computers page. A QR code is the same pairing without typing; a new computer joining through the hub pairs the same way, with the code relayed through it.

What peers say to each other

Pull by origin and sequence; relay what you learned from others with their signature intact; presence every ten seconds while connected.

  • Pull with cursors. A peer asks "give me <origin> since sequence N" for every origin it knows, so a computer that was off catches up exactly, and nothing is sent twice.
  • Relay, keeping the author. Entries are signed by the computer that wrote them, so DEVELOPMENTPC can hand LAPTOP what it learned from WORKPC and LAPTOP can verify it. Three computers that are never all on together still converge.
  • Presence over the connection. Every ten seconds while connected: the running sessions, their project and account, and the last five minutes' tokens. This is what makes the routes live within a second; the one-minute presence file in the folder and the hub's WebSocket are the fallbacks.
  • One port, outbound first. The listener takes a high port and announces it; Windows asks once about the firewall. Where a computer may not listen at all, it connects outbound to the hub and everything is relayed.
Recommendation. Phase 2 ships pairing, mDNS and VPN names, and presence over the connection: that is live routes at home and over Tailscale. Hub rendezvous and relay come with the hub phase, which is what brings the work computer in without a VPN.

What Codex Astra said

Codex Astra (OpenAI Codex, gpt-6.1-sol at high reasoning) read the same brief and the repository, read-only, and answered in its own words. The review went through the Codex CLI because a native subagent cannot be routed to that model. What follows is its position, then where we agree and where we do not.

agreesThe journal is right; the details need tightening

  • Replicate changes, not rows past a timestamp. An old reply can gain corrected tokens or timings later (a resumed session, a longer-timed copy), so the journal must carry an outbox of changes, written in the same transaction as the change, with a sequence number per computer. Deletions need tombstones, so a computer that was off does not bring a removed tag back.
  • Identity beyond a name. A random device id plus an incarnation id, so a formatted computer that restores its history never writes with the same sequence as its old self. Profiles need stable ids too, because today two computers only share an account by its name.
  • Resolve the project key where the session ran. Today the importer stores the cwd and the project key is worked out locally; on the source computer the remote URL is known, on another it is not. Path-only projects need an explicit alias across computers.
  • Definitions that stop double counting. "This computer" means executed here, not "visible here"; "All computers" counts unique requests; cache hit comes from summed tokens, never from averaged percentages; limit readings are observations of one shared limit and are never added up.
  • Freeze the cost. Keep each row's valuation with the price snapshot and its version, and let a current-price revaluation be a separate, optional view. (The draft said "compute at display time"; Astra is right that history should not move when the price table does.)
  • Security by allowlist. Never export kv or the ledger wholesale; transcripts, prompts, MCP configuration and skills can contain secrets, so metadata-only is the default, transcripts are opt-in per project, and transcripts at rest in any shared place are encrypted with a recovery key you hold outside the computer.

differsWhich transport first

Astra ranks B, peers over a VPN first, with explicit addresses and pairing and mDNS deferred, because R3 asks for computers that talk to each other and the folder never delivers that; C, a hub second, if computers are rarely on at the same time; A, the folder only as a history and backup transport, if delayed presence is accepted and R3 is postponed. Its words: "I disagree with unconditional folder-first: it optimizes implementation effort while postponing an explicitly requested behavior."

My reply: the folder gives you R1, R4 and R5 on the day it ships and works from any network you already sync from; peers give the live picture but only while both computers are on and reachable, and a work computer may not allow a VPN. The two are not exclusive: the journal format is the same, and the Computers page already shows how each computer was last heard from. So the real question for you is what to build first, and it is the first question on the feedback sheet. If you choose peers first, phase 2 below becomes pairing and pull over the VPN, and the folder becomes phase 4's backup location.

correctsResuming, per tool

  • Codex. Resume looks the session up in its state database, checks the rollout's thread id, and falls back to scanning file names; so a copied rollout with its original name can be found, and that needs a test per supported release. Run it as codex -C <checkout> resume <id>, so the working folder is set by the command rather than by rewriting the recorded cwd in the file.
  • Claude Code. Current releases also accept --resume <absolute path to the transcript> and search other project folders by id, so the folder-naming dance may not be needed on a current version; what the recorded cwd does to permissions and file paths still has to be checked per release. Hand-copied duplicates make the id lookup ambiguous, so one materialized copy only.
  • OpenCode. It has its own export and import commands (v2: opencode session export / import, with a destination folder), which beats writing into its database.
  • Antigravity. Conversations are protobuf blobs in per-conversation databases, and resume checks a workspace-keyed cache and the backend; view-only until an experiment proves otherwise. Same as the draft.

The three tool claims are checked against the tools' current documentation in the session table above; where a page did not say it, the table says so.

addsThings the draft missed

  • A connected app does not prove a tool is running: presence must come from the running-sessions check, not from the connection.
  • Peers must relay what they learned from other peers, keeping the origin's identity, or three computers that are never all on together never converge.
  • OneDrive placeholders, paused sync and sleeping computers all look like "no news"; the Computers page must show what each computer has contributed up to (its sequence), not just when it was heard from.
  • The Projects page starts from discovered sessions, so a project whose transcripts were archived would vanish; the project list must come from the durable history.
  • Limit history is pruned at 60 days today; the journal should keep it.
  • A transcript does not carry uncommitted files, attachments or running shells; "Resume here" must say so.

Recommendation and plan, in your order

Both ways to sync, one journal: the shared folder ships in phase 1 and the hub in phase 5, and each computer picks one of the two in Settings, with the direct connection on top of either. The order below is the one you chose, with the direct connection moved up because live routes must be within a second, and the hub after backup because the folder and the peers already cover every computer that can run a VPN. Pi, Oh My Pi and DeepSeek are a separate track that does not touch the sync code and can run alongside any phase.

1
Journal and merge, folder transport, Computers section, "All computers" views. Device identity with incarnation, stable account ids, the outbox journal, the merge with a device column and tombstones, frozen costs, the Overview switch and tiles, the Activity grid with its per-computer switch and one time zone, Projects and Sessions counts, the header chip. Folder services: OneDrive, Google Drive, SMB, NAS. About 3 weeks.
2
Direct connection and live presence. Key pair and certificate per computer, pairing with a code, mDNS and VPN names, mutual TLS, pull with cursors and relay, presence every ten seconds; the routes with computer dots and colours, "Running now" with names. About 4 weeks.
3
Resume here. Transcripts in the journal, encrypted with the device key and a recovery key; the project map per computer; Claude Code by path as a fork, Codex with -C, OpenCode through its export and import; Antigravity read-only; a test per tool against the real tool in CI. About 2 weeks.
4
Backup, archive, Welcome back. The bigger backup; the archive with an age setting (30 days by default) in the sync folder and a folder of your choice; restore as a merge; the first-launch dialog. About 1 week.
5
The hub as the second choice in Settings, with rendezvous and relay. "A hub you host" beside "a shared folder": the VPS compose file (H3) or the Worker (H2), joining with a code, and moving a computer from the folder to the hub with its history kept. The Worker, D1, R2 and the Durable Object, the device tokens, presence over its WebSocket, hole punching and relay for peers; the bucket flavour of the folder transport for a NAS or S3. About 3 weeks.
T
New tools track: Pi, Oh My Pi, DeepSeek. Each is one module behind the Harness trait (home, binary, launch, login, identity, usage import, sessions, resume, running, MCP and skills paths). Effort per tool is in the section above once the research is in. Independent of the phases.
Risks worth knowing before you choose. The tools can change their session formats at any release, so "Resume here" needs a test against each real tool in CI and will sometimes lag a tool update. OneDrive "Files On-Demand" and Google Drive streaming can leave a journal as a placeholder that is not on disk; the reader must ask for it and wait. Hole punching fails on some NATs, so the hub's relay is not optional once the work computer is in. A six-digit code is safe only because the PAKE limits guesses; the code expires in two minutes and three wrong tries end the pairing.
