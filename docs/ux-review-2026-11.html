Summary

  • Navigation, decided. Projects become a first-class sidebar entry (from A). It opens a Projects page with a cost and token distribution summary, a chart, and a card per project (from C, now with cost). Opening a project lands in Sessions with the project rail (from B). The three fit together with no overlap; the mockups below show the whole path.
  • The stale-page problem is one bug. There is no single "something changed, redraw" path. One helper used by every mutation fixes Manage all, the sign-in state, and the cases you have not hit yet.
  • Installers are npm-only in a world that moved to native installers. On your own machine three of the four tools are native installs and one is installed twice. The Apps page cannot read the newest version for any of them, offers an updater command that does not exist for Antigravity, and would install a missing tool with npm even when the vendor's native script is the documented route. Every vendor now publishes a version endpoint the app can read with one HTTP call, so this is fixable without guesswork.
  • Tags, live sessions, bulk skill ticks and the Prompts rename stand as in the first round, with your answers folded in.

Navigation: the combined direction

Three screens, one path: the sidebar entry, the Projects page, and a project opened inside Sessions. Costs are at API list prices, as the Overview already labels them, since subscriptions are not billed per token. The cost per project comes from the same pricing table the Overview uses, summed per project and model.

1. Projects in the sidebar

A Projects entry sits between Accounts and Sessions, with the project count. Below it, up to five pinned projects, each with its live dot and session count; you pin from a project's menu. A pinned project opens Sessions filtered to it. The 1 live count beside Sessions is a link to the live list. Nothing else in the sidebar changes except the Prompts rename.

What the page shows, top to bottom:

  • Five tiles: tokens, cost at list prices with the daily average, sessions, running now (a link to the live list), and the busiest project with its share of tokens and of cost. The two shares differ when a project runs on a cheaper model, which is the point of showing both.
  • The distribution: one stacked bar for the share, then a row per project with its bar, tokens, cost and session count. The segment toggle redraws the same rows by tokens, cost or sessions. The top five plus "others" keeps it readable; "others" expands.

Backend: one new call, projects, returning per project the sessions, tokens, cost, accounts, last activity, live count and the 7-day series. It groups the usage table by project and model and prices each group with the pricing table the Overview already uses. The CLI gets hrm projects with the same columns.

Reaching live sessions

Four changes, all visible in the mockups above and independent of the navigation work.

  1. The "1 live" count beside Sessions becomes a link that opens Sessions with the live filter on. Today it is text.
  2. A live strip in the top bar on every page: a pulsing pill reading "1 live · Bunyan". One running session opens its reading view directly; several open the live list. It disappears when nothing runs.
  3. A "Running now" group pinned to the top of Sessions, whatever the grouping, so a running session never hides inside a fold.
  4. The Overview's "running now" tile, the Projects tile, and the Accounts page's "N consoles open" become links to the same live list.

Behind this, the sessions call gets an open: true filter, and the sessions page state (group, days, query, project, tag, live) moves into the hash so these links are plain URLs like #sessions?live=1.

Tags are free text, created by typing, shared across every tool and account, stored in Harness Manager's own database and never written into the tools' session files. Projects can carry tags too; a project's tag shows on its card and in the project header, and filtering by a tag includes sessions of projects carrying it.

What it takes

  • Database: one table, tags(kind, key, tag), where kind is session or project and key is the existing sessions key or project key. Four operations: tag_set, tag_list (every tag with its counts), tag_rename, tag_delete.
  • Sessions call: a tag filter and a tag grouping; a session with two tags appears under both, untagged ones under one folded group.
  • Window: chips on rows, cards and headers; the editor popover; Group by tag; the filter chip; the Tags section of the rail. Colours come from a fixed palette of six in creation order.
  • CLI: hrm sessions --tag release and hrm tag <session|project> release.

Skills: install for a whole tool, and Manage all

The skills list has no header row, so there is nowhere to put a per-tool control. The MCP list has one, with a count under each tool. A click on "some" or "none" ticks every visible skill for that tool in one backend call. The source filter and search still apply, so "tick all" means "tick all shown", and the header says how many.

Installers: how the Apps page finds and installs the tools

What the code does today, in crates/core/src/apps.rs: it finds each tool on PATH, and if the file sits next to an npm node_modules folder it is an npm install; otherwise it runs --version and, for Claude, OpenCode and Antigravity, assumes the tool can update itself with a fixed subcommand. "Check for updates" asks npm for the newest version and nothing else. "Install" for a missing tool is always npm install -g.

The change in the code

  • apps.rs: replace the three string tables with one Installer record per tool: native folders per OS, install commands per OS, the newest-version URL and how to read it (text, JSON field, manifest), the update command per install kind, package names per manager. About 80 lines of data, no new abstraction beyond the record.
  • Detection: list() looks in PATH and in the known folders, returns every copy with its version and kind, and marks the one PATH runs. The version read stays as it is.
  • Newest: latest() reads the tool's URL with the existing HTTP client; npm only for npm copies. Results are cached in the same apps:latest key.
  • Actions: app_update takes the kind into account; two new ops, app_install(id, method) and app_remove_copy(id, path). All open a terminal as today, so you see what runs.
  • Tests: the terminal log the tests already use records the command; one test per tool and kind asserts the right command, and one asserts the two-copies warning.
  • Risk to say out loud: the Antigravity manifest URL and the Codex channel URL are the vendors' own but undocumented. If one changes, that tool's Newest column shows "could not check" and a link to the vendor page, never a wrong version.

Fix plan

Five phases, each shippable on its own. The first one goes before anything else, since every later feature would inherit the stale-page bug otherwise.

P0

Redraw correctly after every action 1 day

Issues 1, 2, 3, 13, 14, 15.

  • core.js: mutate(fn, okMsg); replace every attempt(...).then(render) and the bare attempt calls on mutating actions.
  • main.rs skill_adopt, skill_install, skill_import: return the sync report instead of failing after the save.
  • accounts.js: terminal sign-ins poll the identity every 2 s and close on success.
  • app.js: the background-refresh event marks the page dirty when a dialog is open; dialog close redraws.
  • Tests: one window test per fixed action asserting the page shows the new state without navigation.
P1
