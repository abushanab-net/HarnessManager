Why pages are slow to open, and how to fix it

Measured on this computer's real data on 5 November 2026: 8 accounts, 8,362 Claude Code session files (4.9 GB), 2,767 Codex rollouts (3.1 GB), 8,382 sessions in the index, 296,000 usage rows. The question was whether the pages are slow because every open scans the logs, and whether an index that is updated only on change would fix it. The answer: the index already exists and the per-file signature (size and time) already does what a hash would do; the time goes elsewhere, and most of it is one bug.

Why switching tabs feels worse than these numbers. The app refreshes usage every five minutes in the background, and that refresh is the 36-second import above. The database is behind one lock, so a page opened during those 36 seconds waits for each file's empty commit to finish before its own query runs. A tab switch that lands during a refresh can take ten seconds and more for nothing. The Sessions page also opens two full scans (sessions and projects) and the sidebar's pinned projects open a third at start-up.

Is it the scanning? Is hashing the answer?

  • The scan itself is cheap: stat-ing 11,000 files is about 0.3 seconds. What costs is what the code does per file afterwards: a lock, a query, and for the import a write transaction, 8,362 times.
  • Hashing file contents would be slower than today, since it means reading every file (8 GB) on each refresh. The current signature, size plus modification time with a 32-byte tail check, is the right cheap "hash"; it correctly reports that nothing changed. The problem is that the code then does the expensive thing anyway.
  • An index already exists: the sessions and cursors tables. The pages just do not read from it directly; they rebuild the list from the filesystem on every open and consult the index one row at a time.

Options

1Fix the per-file waste (hours)

  • No transaction when a file brought no rows: the 36-second import becomes about one second. One line.
  • Read Codex rollouts from a cursor like Claude's, so an active 145 MB rollout is read from where it was left: 3 seconds become milliseconds.
  • Load the cached session records in one query per account (a map by file path), then stat the files: the per-file lock and query go away. 2.8 seconds become about 0.2.
  • Journal a session only when its activity time moved, decided in memory against that map: 8,362 write statements become a handful.
  • One scan per render: the Sessions page and the sidebar use the result the Projects page just computed (a short-lived cache keyed by the refresh generation).

Expected: Sessions page from about 6 s to under 1 s warm; Projects the same; the refresh from 40 s to about 2 s, so a tab switch during a refresh no longer waits. Risk: low; the tests cover import counts and the cursor logic.

2Read the pages from the index, scan only in the background (days)

What you described. The sessions table becomes the source the pages read: SQL with paging, sorting and filtering, including the search (an FTS5 index over title and folder for very large histories). The filesystem is touched only by the background refresh, which updates the index and emits the existing changed event, and the pages refresh in place. A page open is then one query of tens of milliseconds regardless of how many files exist.

Expected: every page opens in well under half a second, and the time stops growing with the number of sessions. Risk: medium: the ordering of "what is open now" and the first paint after start-up (before the first scan) need care; the e2e suite that seeds files and expects them on the page must wait for the refresh instead of a page open.

3Watch the folders instead of polling (days, after 2)

A file watcher on the tool folders (the notify crate) updates the index within a second of a file change and re-reads only that file, from its cursor. The five-minute refresh stays as the safety net. Usage, sessions and live routes then follow the tools in real time, and the periodic full walk disappears.

Expected: near-instant freshness and a quieter disk. Risk: medium: watchers on Windows can drop events under load and need the periodic walk as a fallback; OneDrive-backed folders generate noise.

4Keep pages warm in the window (hours, after 1)

Switching tabs today re-fetches everything. Keep the last answer of each page in memory and show it at once, then refresh it in the background and redraw if it changed; virtualize the long session lists so 8,000 rows do not sit in the DOM. This makes a switch feel instant even before option 2 lands.

5Shrink what is scanned (optional)

The archive from phase 4 moves old transcripts out of the tool folders; with a 30-day archive age the live folders hold a few hundred files instead of 11,000, and every scan shrinks with them. This is already built; it only needs the setting turned on.

After option 1, measured the same way (1.6.2)

The cause turned out to be one primitive more than the empty transactions: on Windows, Rust's file metadata call opens a handle per file, about half a millisecond each with the antivirus looking on, and every refresh and page open made two of those per file across 11,000 files. The directory listing already carries size and time, so the walks now use that, nothing opens a file that did not change, and a session still being written shows its cached record while the file is parsed again in the background.
